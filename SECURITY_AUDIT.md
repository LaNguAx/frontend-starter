# Dependency Security Audit

**Project:** frontend-starter (Vite + React + TypeScript scaffold)
**Audit date:** 2026-08-17
**Scope:** all 32 direct dependencies — the exact versions the `~` (tilde) ranges in `package.json` resolve to as of the audit date.
**Method:** 7 parallel Opus 5 audit agents. Per package: registry release-cadence analysis (`npm view time`), npm provenance attestation check (`dist.attestations`), install-script inspection (`scripts`), changelog review of the exact release (GitHub releases/CHANGELOG, tarball diffs where warranted), and advisory/incident research (GitHub Advisory Database, Snyk, security press). Plus one ecosystem-wide sweep of 2025–2026 npm supply-chain incidents checked against every package@version pair in this list.

## Executive summary

**Every one of the 32 pinned versions is approved for use. 12 clean approvals, 20 approve-with-notes, 0 holds.** No package@version pair in this list matches any known-malicious release: each pair was checked individually against the OSV.dev/GHSA advisory feed (including the OpenSSF MAL-\* malicious-package feed) and exact-matched against three vendor IOC datasets from the 2025–2026 npm attack waves (Shai-Hulud 2.0, chalk/debug, keyv/cacheable). The check harness was validated with positive controls, so the clean result is meaningful, not a silent failure.

### Do NOT downgrade these two

- **`react-router@8.3.0` is itself a security fix** for GHSA-qwww-vcr4-c8h2 (High, CVSS 7.1, RSC-mode CSRF bypass). Every 8.x version below 8.3.0 is vulnerable — there is no "safer older patch" here.
- **`vitest@4.1.10` is itself a security fix** for CVE-2026-73653 (Critical, CVSS 9.4, Browser Mode file-access bypass). Pinning anything earlier in the 4.x line is strictly worse.

### Action items (ordered by importance)

1. **Commit a lockfile — this is the single biggest gap.** The repo has no `package-lock.json`, and tilde ranges do not pin the *transitive* tree. The risk is not hypothetical for this exact stack: `eslint` depends on `debug ^4.3.2`, and `debug@4.4.2` was a malicious build live on the registry for ~2 hours on 2025-09-08 — an unlocked install in that window would have resolved it. Run `npm install --package-lock-only` and commit the result; use `npm ci` for all subsequent installs.
2. ~~Delete the vendored `msw-2.14.7.tgz` from the repo root.~~ **Corrected:** the tarball (and the extracted `old/package/` directory) were artifacts of *this audit itself* — the auditing agents downloaded registry tarballs for byte-level diffing in the working directory instead of a temp location, and the sweep agent then misidentified the leftovers as user-vendored files. The tarball was hash-verified authentic and has been removed; delete the leftover `old/` directory too. No vendoring decision is needed. (See *Post-audit corrections* below.)
3. **If `eslint-config-prettier` is ever added back, require ≥ 10.1.8.** The July 2025 phishing incident (CVE-2025-54313) poisoned `eslint-config-prettier`, `eslint-plugin-prettier`, `synckit`, `@pkgr/core`, and `napi-postinstall`. The core `prettier` and `eslint` packages in this list were never affected.
4. **Know the one install hook in the set:** `msw` has a real `postinstall` script. It was extracted and read during this audit — benign, long-standing, byte-identical to prior releases — but it is the only package here that executes code at install time.

### Anomalies investigated and cleared

Four release patterns matched the classic shape of a supply-chain compromise; each was investigated in depth and found benign:

- **`date-fns@4.4.0`** — 20-month dormancy, then 4 releases in 11 days. Cleared: the package *shrank* by 10 MB (CDN builds extracted to a separate package), zero deps, zero scripts.
- **`react-redux@9.3.0`** — 17-month release gap. Cleared: coordinated same-day Redux release, a one-line deprecation diff, and the release *restored* OIDC trusted publishing (9.2.0 had been a manual personal-token publish).
- **`react-i18next@17.0.11`** — its `<Trans>` parser dep `html-parse-stringify` was revived after 5 years dormancy under a new repo/publisher, 6 minutes before this release. Cleared: publicly documented legitimate handover to the i18next org; original owners retained; no install hooks anywhere in the chain.
- **`@testing-library/dom@10.4.1`** — no provenance, 370-day gap, Sunday publish via shared bot token. Cleared: content matches changelog exactly, tarball got smaller, and it has since had 386 days of massive-volume exposure with zero advisories.

### Residual structural risks (accepted, worth recording)

- **No provenance attestation** on: `typescript@6.0.3` (published by the `typescript-bot` token, not OIDC), `prettier@3.9.6`, `@testing-library/dom@10.4.1`, `eslint-plugin-react-hooks@7.1.1`, and `clsx@2.1.1`. Everything else in the list is SLSA-attested via GitHub Actions trusted publishing.
- **Solo-publisher packages** (`zod`, `date-fns`, `clsx`, `tailwind-merge`, `msw`, `eslint-plugin-react-refresh`): a single npm account is the publish surface. Mitigated where the project uses OIDC trusted publishing (zod, tailwind-merge, msw, eslint-plugin-react-refresh do; clsx does not).
- **`clsx@2.1.1`** has had no release in over two years — extremely battle-tested (102M weekly downloads, zero advisories ever), but a future hijack would land directly in the runtime tree.
- **`typescript ~6.0.2` resolves to 6.0.3**, a generation behind the 7.x line — fine and deliberate (ecosystem compatibility), but it means security fixes now land primarily on 7.x.

All statements below about a vendored tarball (§6.4, §7, sweep qualification 4) are superseded. The tarball's authenticity verification remains valid — it matched registry hashes exactly.
2. **The manifest has since moved to exact pins.** All references below to `~` ranges and `save-prefix=~` describe the state at audit time; `package.json` now pins the exact audited versions and `.npmrc` is `save-exact=true`.
3. **Still outstanding:** committed `package-lock.json` (action item 1) — the transitive tree remains unpinned until then.

## 2. Maintainer account takeover via phishing

### 2.1 July 2025 — `npnjs.com` phish → ESLint/Prettier tooling (CVE-2025-54313)

**What happened.** On 2025-07-17 a phishing mail impersonating npm support pointed maintainer `JounQin` at the lookalike domain `npnjs.com`; credentials entered there yielded a working npm token. Malicious releases followed on 2025-07-18.

|---|---|---|

## 3. Self-replicating worms (the dominant 2025-2026 pattern)

### 3.1 Shai-Hulud 1.0 — September 2025

Detected 2025-09-15 via `@ctrl/tinycolor`. Anchor malicious versions include `@ctrl/tinycolor@4.1.1`/`4.1.2` (confirmed: MAL-2025-47141), plus `@crowdstrike/*`, `ngx-bootstrap`, `ngx-toastr` releases. ~200 packages / 500+ versions between Sept 14-18; CISA issued a `widespread supply chain compromise` alert on 2025-09-23. Mechanism: install-time credential harvesting (npm/GitHub/AWS/GCP tokens) exfiltrated to attacker-created public GitHub repos, then self-propagation by republishing every package the stolen npm token could reach. **Status:** contained; CISA advisory and CERT/CC VU#534320 remain the reference.

### 3.2 Shai-Hulud 2.0 / "The Second Coming" — November 21-24 2025

The largest npm event to date: **796 unique backdoored packages** (Datadog's verified count), 25,000-27,000 malicious GitHub repos, ~14,000 secrets exposed across ~487 orgs. Patient zero was the `asyncapi/cli` repo; other trojanized org scopes included Zapier, ENS Domains, PostHog, and Postman. Key escalation: execution moved to the **`preinstall`** hook, plus persistence via self-hosted GitHub Actions runners and a destructive dead-man's switch.

**Caught by** querying GitHub's public event archive for repos described `Sha1-Hulud: The Second Coming`. Last observed malicious publish 2025-11-24 18:00 UTC.

**I downloaded Datadog's two IOC CSVs and diffed them against your 32 package names — zero exact matches.** The nearest misses are instructive, because they are *name-adjacent* to your stack:

- `@ensdomains/vite-plugin-i18next-loader@4.0.4`
- `@lui-ui/lui-tailwindcss@0.1.2`
- `@seung-ju/react-hooks@0.0.2`
- `okta-react-router-6@5.0.1`

None of these is `vite`, `i18next`, `tailwindcss`, `eslint-plugin-react-hooks`, or `react-router`.

### 3.3 "Shai-Hulud: The Third Coming" — April 22 2026 (Bitwarden CLI)

`@bitwarden/cli@2026.4.0` (confirmed: MAL-2026-3020), published via a poisoned GitHub Actions workflow, live ~90 minutes, ~334 downloads. Detection signal called out repeatedly: package ballooned from ~200 KB to ~4.29 MB. The payload specifically hunted credentials for **AI coding tools** (Claude Code, Cursor, Codex CLI, Aider, Gemini CLI) alongside SSH/cloud/CI secrets. User password vaults were not affected. Linked to the financially motivated actor **TeamPCP**; the same cluster also hit Trivy (Docker images 0.69.4-0.69.6), LiteLLM (PyPI 1.82.7/1.82.8), and Checkmarx.

### 3.4 "Mini Shai-Hulud" waves — April-June 2026

Per Unit 42's tracker (I could not independently confirm every version string, so treat the counts as vendor-reported):

- **Apr 29** — SAP CAP ecosystem: `@cap-js/sqlite@2.2.2` (confirmed MAL-2026-3178), `@cap-js/postgres@2.2.2` (confirmed MAL-2026-3177), `@cap-js/db-service@2.10.1`.
- **May 11** — **TanStack** GitHub Actions pipeline hijack: 42 `@tanstack/*` packages, 373 malicious versions. Reported as the **first documented case of malicious npm packages carrying valid SLSA Build Level 3 provenance** — provenance proved *where* it was built, not that it was safe. Self-propagated onward to UiPath, Mistral AI, OpenSearch packages.
- **May 12** — toolchain source published publicly, enabling copycats.
- **May 19** — `@antv` / charting ecosystem: reported 639 malicious versions across 323 packages in one hour; `echarts-for-react` (~1.1M weekly downloads) affected.
- **Jun 1** — **Miasma**: 32+ packages under `@redhat-cloud-services`.

**Relevance:** you use none of these. But TanStack is the closest analogue to your stack in tooling shape, and the SLSA-signed-malware detail directly constrains how much weight to put on provenance (§7).

### 3.5 AsyncAPI — July 14 2026 (`miasma-train-p1`)

Release pipelines of four AsyncAPI repos compromised via unprotected pre-production branches. `@asyncapi/generator@3.3.1`, `@asyncapi/specs@6.11.2` (confirmed MAL-2025-190643 + IN-MAL-2026-010499/010505), `@asyncapi/specs@6.11.2-alpha.1`, `@asyncapi/generator-helpers@1.1.1`, `@asyncapi/generator-components@0.7.1`. Notable for canary rollout (5% initial targeting, scaling in 100-unit waves) to stay under scanner thresholds, and IPFS/Ethereum/Nostr/BitTorrent-DHT C2.

### 3.6 `keyv` / `cacheable` — August 4 2026 (most recent, 13 days ago)

GitHub maintainer account hijacked at 09:00 UTC; malicious publish propagated to **400+ npm packages**. Confirmed versions: `keyv@6.0.0` (MAL-2026-11524 + IN-MAL-2026-010972), `cacheable-request@13.0.20`, `cache-manager@7.2.10`, `@cacheable/utils@2.5.1`. Vector: a `preinstall` hook running obfuscated code before app code, with an Ethereum smart contract as dynamic C2. **Status: recent — treat as still-settling.** Wiz maintains the running package list.

**Relevance:** `keyv`/`cacheable-request` are `got`/HTTP-client transitives. Not present in your direct list, and none of your 32 deps declare them (I checked the dep manifests of `vitest`, `msw`, `jsdom`, `@testing-library/dom`, `vite`, `eslint` — none pull `keyv`).

### 3.7 `node-ipc` — May 14 2026

`node-ipc@9.1.6`, `9.2.3`, `12.0.1` published simultaneously with an identical ~80 KB credential stealer (confirmed `12.0.1` → MAL-2026-3744). Not in your tree.

## 7. Registry-level defenses for this project

Ordered by leverage-per-effort for *this* repo. Your installed npm is **11.12.1**, which supports everything below.

**1. Commit a lockfile and install with `npm ci`.**
`npm ci` installs the exact resolved tree from `package-lock.json` — including integrity hashes for every transitive — and refuses to run if the lock and `package.json` disagree. This is the single highest-value fix here, because right now there is no lockfile at all, and it is the only control that would have blocked the `eslint → debug@4.4.2` path in §6.3.
*Trade-off:* the lock must be regenerated and reviewed on every dependency change, and `npm ci` wipes `node_modules` each run, so local installs are slower. It also pins you to known-good *and* known-bad alike — a stale lock keeps a vulnerable version until someone updates it.

**2. Set a cooldown: `min-release-age=1` in `.npmrc`.**
Available in npm CLI ≥ 11.10.0 (Feb 2026), expressed in **days**. Refuses to resolve any version published more recently than the threshold. Every fast-response incident in this report was pulled inside that window — chalk/debug under 2 hours, axios ~3 hours, Bitwarden CLI ~90 minutes, ViteVenom's packages days. A 24-hour gate neutralises the entire smash-and-grab class.
*Trade-off:* it delays legitimate security patches by the same interval, which is the wrong direction during an actively exploited CVE. Keep an exclusion path for hotfixes, and configure Renovate/Dependabot's own cooldown separately — the gate applies at install time, not when the bot opens the PR. (pnpm's `minimumReleaseAge` is in **minutes** and defaults to `1440` in pnpm 11; Yarn Berry ≥4.10 uses `npmMinimalAgeGate`, also minutes — avoid duration strings like `"7d"` there due to a known parsing bug.)

**3. `ignore-scripts=true` in `.npmrc`, with an explicit allowlist.**
Blocks `preinstall`/`postinstall`/`install` hooks — the execution vector for Shai-Hulud 2.0, the Third Coming, `keyv@6.0.0`, and the `eslint-config-prettier` DLL loader. It is the difference between "a bad tarball is on disk" and "the attacker has your `~/.npmrc`, SSH keys, and CI tokens."
*Trade-off:* **it is not a complete defense** — the chalk/debug crypto-clipper ran no install script at all; it lived in the shipped bundle and executed in the browser. And it will break legitimate hooks: `msw`'s `postinstall` copies the service-worker script into `public/`, so you'd run `npx msw init ./public` manually. Native-build packages break too. pnpm 10+ blocks builds by default and expects an `allowBuilds` allowlist; prefer that over globally re-enabling.

**4. Pin exactly, and verify signatures in CI.**
Change `.npmrc` from `save-prefix=~` to `save-exact=true` so `package.json` records `19.2.8`, not `~19.2.8` — removing the floating patch digit that malicious republishes exploit. Then run `npm audit signatures` in CI to check registry signatures and SLSA provenance attestations for the installed tree.
*Trade-off:* exact pins mean every patch bump is a manual PR — real friction on a 32-dependency project, and it invites pin rot if nobody tends it. More importantly, **provenance proves origin, not intent**: the May 2026 TanStack wave shipped malicious packages carrying *valid SLSA Build Level 3 provenance*, because the attacker owned the build pipeline. Treat signature verification as tamper-detection between build and registry, never as a safety verdict.

**5. Reconcile the vendored tarball.**
`msw-2.14.7.tgz` and `old/package/` are authentic (§6.4), but they live outside every control above — no lock entry, no audit coverage, no cooldown, no signature check on future use. Either install `msw` from the registry at your intended 2.15.0 and delete both, or, if vendoring is deliberate, record the verified SHA-512 somewhere a reviewer will actually check. *(Superseded — audit artifact, since removed; see "Post-audit corrections".)*
*Trade-off:* registry installs reintroduce dependency on registry availability and on npm's own integrity — which is precisely what vendoring was avoiding. Pick one and document why.
